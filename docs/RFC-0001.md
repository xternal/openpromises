## 1. Summary

Three projects track what people in power promise, with the same idea: a promise is a card with the speaker's exact words, a cost with its source, and a timeline that moves only on evidence and is never rewritten. Each project has written its own code for it, and the copies have drifted. This RFC proposes **OpenPromises**: one open-source engine, used by all three and by anyone else, that holds the rules (card format, status ladder, append-only history with public corrections, two-editor approval, exact-quote checks) and the shared machinery (validation command, intake from transcripts, the automated reviewer, feeds, search and AI publishing, page components). Each site keeps its own brand, data pipeline, financial model and pages, and sets the engine up with a configuration file: languages, who can be tracked, statuses and their labels, topics, currency.

Recommended: Apache-2.0, a repository under the owner's GitHub account, TypeScript core plus JSON Schema, static-site friendly, built after Budget day (28 October 2026) in four steps over about four weeks.

## 2. Why now

**Three copies, drifting.** Public Ledger built the most complete version. Borough Book rewrote it more simply and added council concepts. Russia Ledger copied it and made it stricter and bilingual. Their field names and shapes now differ almost everywhere: `actor_id` against an `actor` object, where cost lives, reply shapes, status lists, labels. Every fix lands in one project and not the others:

* Borough Book cannot record a correction: any fix to a past entry fails CI. Public Ledger solved this in October (corrections with an undo check).
* Borough Book's append-only check is sensitive to YAML key order and breaks when its schema changes. Public Ledger's compares normalised entries.
* Russia Ledger records editors' approvals in the card and refuses a review from an editor about their own party. Public Ledger counts GitHub reviews and has no party check in code.
* Russia Ledger checks that the first event is the promise, that events are in date order and that the status has a matching event. The others do not.

**The right moment for each.** Public Ledger is mature and has a launch on 28 October, so it moves first, after that date. Borough Book has 18 cards and a simple schema, so it moves second. Russia Ledger is building its promise ledger now (milestone M5, first cards being approved), so it can adopt the engine instead of growing a fourth variant.

**Beyond these three.** Newsrooms, councils and projects in other countries could run a promise tracker with a configuration file and a folder of cards, instead of rebuilding one. That is the reason to make it open and permissive.

## 4. Goals and non-goals

**Goals**

1. One card format and one set of rules, configured per site, never forked.
2. Content stays plain files in git (YAML), so every change is a reviewable diff and history is public.
3. Works for a static site with no server; a server only for optional features (submissions, email alerts).
4. Every language a site needs, in every text field we write; the speaker's words always kept as said.
5. The rules that make the ledger trustworthy are enforced by code and tests, not by goodwill: exact quotes, evidence before status, append-only history, public corrections, two editors, no editor approving their own party, one standard for everyone.
6. Each site can add its own fields and links (wards, contracts, indicators) without changing the engine.

**Non-goals**

* Financial models: Public Ledger's tax-and-spend engine, Borough Book's council budget rules and Russia Ledger's fiscal rules stay separate (as `SHARED_CORE.md` decided). A card links to a lever by id; that is all.
* Data pipelines (ETL) and statistics.
* A hosted service or CMS. OpenPromises is a library and a command-line tool.
* Judging people. The engine records what was said and what happened; labels stay neutral.

## 5. Principles the engine enforces

1. **Exact words.** A card quotes the speaker word for word from a stored or archived source; a quote that is not found at the source cannot be published.
2. **Evidence moves status.** Every status event after "promised" needs an evidence link; the ladder only climbs on evidence.
3. **Nothing is rewritten.** Versions, events and replies are append-only. Our own mistakes are fixed in place only with a recorded correction (date, old value, new value, reason, source), and the check proves that undoing the corrections gives back what was published.
4. **Two editors.** A card is published only with two editors' approval; an editor never approves a card about their own party.
5. **One standard.** No rule, label or code path depends on which party is involved. A conformance test runs every rule on cards from every party.
6. **Numbers carry their source.** A cost is a range with a quality label and a source; a single figure becomes a range with a stated editorial margin.
7. **Machines suggest, people decide.** Intake and the automated reviewer produce drafts and review notes, never published cards.
8. **Privacy by default.** No tracking, no accounts; any follower data stays on the site's own server and is never exposed per person.

## 6. Architecture

A monorepo, `github.com/xternal/openpromises`, published to npm under the `@openpromises` scope (an npm organisation owned by the same person; package names stay neutral whatever the repository's home).

| Package | What it does | Comes from |
|---|---|---|
| `@openpromises/core` | Card format (Zod schemas and exported JSON Schema), types, rules: status ladder, events, evidence, corrections replay, append-only diff, approvals and conflicts, headline rules, cost ranges, cross-field checks. Pure functions, no I/O. | Public Ledger `content.ts`, `promises.ts`; Russia Ledger's stricter checks and approvals |
| `@openpromises/files` | Reads and writes a content folder (cards, actors, editors, drafts), compares with a git base, migrates format versions. | Public Ledger `content-files.ts`, `validate.ts`; Russia Ledger `content-data.ts`, `scripts/content.ts` |
| `@openpromises/cli` | `openpromises validate` (schema, rules, append-only against the base branch, drafts), `new`, `review` (record an approval), `check-quote`, `deadlines` (append `deadline_missed`), `lint` (neutral words, per language), `stats`. | Public Ledger `validate.ts`, `deadlines.ts`; Russia Ledger `review.ts`, `lint:words` |
| `@openpromises/quotes` | Exact-quote matching: normalisation per language (Russian ё/е, quotation marks, dashes, spaces), tiers exact / close / none, spans in stored text or archived captures. | Public Ledger drafts span check; Russia Ledger `quoteKey`, `etl/quotes.py`; Borough Book decision-link quote check |
| `@openpromises/intake` | Turns transcripts and documents into draft cards that quote only stored text. Source adapters (Hansard, GOV.UK, ModernGov council minutes, Kremlin and Duma, uploads); a model interface for extraction (any provider). | Public Ledger `harvest`; Borough Book `decision-links` |
| `@openpromises/reviewer` | The automated reviewer ("AI Journalist"): a checklist and runner that writes review notes and flags, never approvals. | Public Ledger reviewer brief; Borough Book editor checks |
| `@openpromises/publish` | Built at build time: Atom/RSS feeds (all, per card, actor, topic, place), JSON-LD (CollectionPage, Article with Quotation, breadcrumbs; no ClaimReview), Markdown per card, `llms.txt` and `llms-full.txt`, sitemap entries, IndexNow, open data (JSON and CSV). | Public Ledger `seo`, `alerts/feed`, `api`; Borough Book `feeds`, `structured` |
| `@openpromises/react` | Server components that render without JavaScript: promise list with filters, card page (quote, status ladder, cost, timeline, corrections, replies, earlier wording with a diff), "coming up" deadlines, actor and topic lists. Themeable, translatable; small client parts only where they help (filters). | Public Ledger `PromiseDetail`, `PromiseList`, `PromiseIndex`, `ComingUp`; Russia Ledger `PromisePage`; Borough Book `PromisesIndex` |
| `@openpromises/follow` *(later, optional)* | Change detection and fan-out to email and Telegram with Postgres, under the privacy rules (counts only above a threshold). Static sites use the feeds from `publish` instead. | Public Ledger `follow`, `alerts` |

Python pipelines read the exported JSON Schema; no Python port of the rules.

## 7. Configuration, not code

Each site has one file, `openpromises.config.ts`:

```ts
import { defineConfig } from "@openpromises/core";

export default defineConfig({
  site: { name: "Public Ledger", url: "https://ledgergov.uk" },
  locales: { default: "en", all: ["en"] },           // Russia Ledger: { default: "ru", all: ["ru", "en"] }
  money: { currency: "GBP", unit: "bn", period: "year" }, // Borough Book: unit "m", plus capital costs; Russia Ledger: "RUB"
  actors: {
    kinds: ["person", "party", "government", "public_body"],
    standing: "manual",                               // Borough Book: "fromSeats"; Russia Ledger: none, with level
    ids: { parliamentMemberId: "uk-parliament" },     // per-country identifiers, all optional
  },
  venues: ["manifesto", "speech", "debate", "tv", "interview", "press_release", "parliament", "social"],
  areas: { kind: "enum", values: ["taxes", "health", /* … */] }, // Borough Book: free text; Russia Ledger: budget section codes
  ladder: "national",                                 // presets below, or a custom ladder
  labels: { failed: "Not met", quietly_dropped: "Undone" },
  editorial: { approvals: 2, model: "in-file", partyConflict: true },
  quotes: { archive: "required", normalise: "en" },
  modules: ["contracts", "corrections", "reviews"],   // Borough Book: "decisions", "wards"; Russia Ledger: "metrics", "designations"
});
```

**Ladder presets.** `national` (promised, in plan, legislated, funded, delivering, delivered), `local` (promised, in plan, budgeted, delivering, delivered, with `not_in_power` for opposition pledges) and `custom`. Every status belongs to a fixed engine category (`open`, `progress`, `finished`, `off_ladder`), so feeds, deadlines and the reviewer work the same whatever the ladder is called. Labels are per language and neutral by default ("Not met", "Undone"; "Не выполнено", "Без продолжения").

## 8. Card format v1

The superset of the three, with site-specific parts in modules. Text we write is a language map (`{en: "…"}`; one language is just one key). The speaker's words stay as said, with optional translations.

```yaml
format: openpromises/1
id: uk-bus-cap-2-2026
headline: { en: "Cap bus fares at £2" }
actor_id: andy-burnham              # actors/<id>.yaml: kind, names, roles, party, standing or level, identifiers, same_as
made_on: "2026-07-22"
venue: press_release
venue_label: { en: Government announcement }
area: transport                      # from the configured list
status: in_plan
status_note: { en: "…" }
versions:                            # append-only; a reworded promise or a moved deadline is a new version
  - version: 1
    text: "I’ve done it before and I will do it again now: a £2 cap on bus fares…"
    translations: {}                 # Russia Ledger: { en: "…" }
    recorded_on: "2026-07-22"
    source_url: https://www.gov.uk/…
    archived_url: https://web.archive.org/…   # required when quotes.archive = "required"
    page: null
    quote_checked_on: "2026-10-06"
    parameters:
      who: { en: Bus passengers in England outside London }
      cost:                          # absent = "cost not stated"; null parameters = unscoreable
        range: [0.36, 0.4, 0.44]
        quality: sourced             # configured label set
        note: { en: "Year shown: 2027…" }
        sources: [{ title: "DfT written statement", url: https://… }]
      capital_cost: null             # Borough Book
      when: { en: 1 January to 31 December 2027 }
      deadline: "2027-01-01"
      funded_by: { en: "An extra £454m…" }   # exactly as stated; null = "Funding not stated"
      funding_verifiable: true       # Russia Ledger: false for classified annexes
      metric: null                   # Russia Ledger module: series, target, direction, by
events:                              # append-only; the first is always "promised"; in date order
  - { date: "2026-07-22", type: promised, text: { en: "…" } }
  - { date: "2026-07-22", type: in_plan, text: { en: "…" }, evidence_url: https://… }
replies: []                          # { from_actor_id | from, date, text, url, editor_response }
corrections: []                      # { date, path, was, now, reason, source_url }
reviews:                             # { by, kind: automated | editor | legal | external, on, note, approves: true|false }
  - { by: AI Journalist, kind: automated, on: "2026-10-06", note: "…" }
links:                               # module data, typed by the site's modules
  contracts: [{ ocid: ocds-h6vhtk-… }]
  decisions: []                      # Borough Book: { decision_id, event, quote }
  lever: bus_cap_2
x: {}                                # site-only fields, validated by the site's own schema
```

**Decisions in this format** (details in §12): cost and deadline live in each version, because rewording a promise usually changes them (Russia Ledger already does this); approvals are recorded in the card (works on any git host and for static sites, and makes the two-editor rule visible in the content itself); drafts are full cards in `content/drafts/`, carrying the stored source and quote span so the quote check runs before any approval.

**Format upgrades are not edits.** Each card states `format:`. The engine migrates old formats on read, and the append-only check compares migrated forms, so moving a project to v1 does not count as rewriting history. Migration commits change the format line only through `openpromises migrate`, which CI recognises.

## 9. How each project moves

**Public Ledger (first, after 28 October).** Mostly renaming: the core is extracted from it. Changes: deadline moves into versions (migration), approvals move from GitHub reviews into the card (the intake merge job then counts approvals in the file; GitHub reviews remain a way to see discussion), `headline` becomes a language map, actor `standing` stays manual. Site code keeps its pages, sandbox, API, follows and Statement; the promise pages use `@openpromises/react` where it fits.

**Borough Book (second).** Gains corrections, reviews, exact-quote checks, a robust append-only check and versioned costs. Mapping: `actor {kind, id}` → `actor_id`; `cost_m` → `cost` with `unit: "m"`; `capital_cost_m` → `capital_cost`; statuses through the `local` ladder (`budgeted`, `not_in_power`); decision links → the `decisions` module (its quote check moves into `@openpromises/quotes`); `side` from seats → `standing: "fromSeats"`. Fixes on the way: the unused `administration` actor kind, three duplicated label tables, the two different "finished" sets.

**Russia Ledger (third, at the end of M5 or with M7).** Already closest to v1 (bilingual, versioned deadlines, approvals in the file, stricter checks). It keeps its static export and privacy rules: no `follow` package, feeds built at build time, components that work without JavaScript and from `file://`. Its `designation_ru` on sources and `metric`/`measurement` become the `designations` and `metrics` modules. The engine is a plain npm dependency: no shared hosting, accounts, telemetry or brand with the UK projects.

## 11. Risks

* **Over-generalising.** The engine grows options nobody uses. Mitigation: only what at least two of the three projects need goes into `core`; the rest is a module or the site's `x` fields.
* **Breaking a live site.** Mitigation: conformance fixtures from real cards; a site moves only when its CI passes and its pages render the same; never in a launch week.
* **History rules versus migration.** Mitigation: migrate-on-read and the `format:` line (§8), so a format change is never mistaken for a rewrite.
* **Maintenance load on one person.** Mitigation: small surface, strong tests, semantic versioning, a changelog; outside contributors through the same two-reviewer rule.
* **Russia Ledger's safety.** A shared public dependency reveals only that it uses an open library. The repository sits under the owner's personal GitHub account (decision 2), so a dependency points to the same person who owns the UK project; Russia Ledger's own decisions on who is visible (D3) should take that into account. Mitigation: neutral package names and branding; no telemetry, no network calls from the engine; the Russia project pins versions and can vendor the code (copy it into its own repository) if it ever needs no visible link.
